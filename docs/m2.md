# M2: jedna domena, mocki systemów, serwery ws-04

Adres publiczny portalu i gateway'a: `https://localhost:18745` (`PROXY_TLS_PORT` w `.env`). Przeglądarka i klienci MCP
widzą jeden origin; serwery MCP są osiągalne tylko przez gateway. Ten sam proxy słucha też po http na `:18740`
(`PROXY_PORT`, te same trasy i reguły, bez przekierowania), ale `MCP_PUBLIC_URL` gateway'a, `PORTAL_PUBLIC_BASE_URL`
BFF i `MCP_PORTAL_URL` brokera są adresem https: linki, `resource_metadata`, callback OIDC i OAuth wskazują https.
Powód: Safari nie zapisuje ciasteczek `__Host-`/`Secure` z `http://localhost`, więc logowanie do portalu po http
kończyło się "Sesja wygasła". Klient, który loguje się przez `:18740` (np. skrypt z własnym słowniczkiem ciasteczek),
zostanie przekierowany na https przez BFF i nie dokończy logowania; używa się `:18745` z CA z `certs/public-ca/ca.crt`.

## Krok po kroku dla człowieka

Wszystkie ścieżki względem katalogu repo (`mcp-platform-dev`). Stos działa (`make up-m2`).

1. `make trust-ca` wypisuje dwa polecenia. Uruchom pierwsze (`security add-trusted-cert ...`, hasło logowania albo
   Touch ID); zrestartuj przeglądarkę.
2. W powłoce, z której startuje Claude Code: `export NODE_EXTRA_CA_CERTS="$PWD/certs/public-ca/ca.crt"`.
3. `make users` pokazuje hasła `alice`, `bob`, `carol`, `mallory`.
4. Otwórz `https://localhost:18745` (Chrome, Firefox albo Safari) i zaloguj się jako `alice`; formularz Keycloaka jest pod
   `https://localhost:18746`.
5. W portalu: katalog, "Dodaj PAT" dla Jiry (`alice-pat`), "Połącz przez OAuth" dla GitLaba, potem nowy link z wybranymi
   narzędziami. Portal pokazuje gotową komendę.
6. `claude mcp add --transport http --client-id claude-code --callback-port 33418 <nazwa> https://localhost:18745/v/<slug>/mcp`
   (port 33418 wolny); w Claude Code `/mcp`, `Authenticate`, logowanie jako alice w tej samej przeglądarce.

Skutki uboczne testów: `make m2` tworzy i usuwa linki oraz zapisuje PAT Jiry alice (i `bob-pat` jako test cudzego PAT, potem
`alice-pat` z powrotem), łączy i rozłącza GitLaba alice; po przebiegu zostaje PAT alice, a stan połączenia GitLab zależy od ostatniego kroku scenariusza.
`make m1` zatrzymuje i uruchamia z powrotem kontener brokera (`docker stop/start`, scenariusz A15): na czas
przebiegu, do healthchecka, broker jest niedostępny dla wszystkich korzystających ze stosu.

### HTTPS i zaufanie do CA

- Certyfikat serwera dla `localhost` wystawia osobne CA "dev public" (`certs/public-ca/`, `make certs`), nie wewnętrzne
  CA od mTLS. Wewnętrzne CA nie ma ograniczeń nazw i podpisuje tożsamości komponentów; dodanie go do pęku kluczy
  uczyniłoby je zaufanym dla każdego hosta. CA "dev public" ma name constraints (`localhost`, `127.0.0.1`, `::1`),
  więc zaufanie do niego niczego poza lokalnym proxy nie obejmuje. Klucz CA jest tylko w `certs/public-ca/ca.key`
  (git-ignored, nie montowany do żadnego kontenera); do proxy trafiają `tls.crt` i `tls.key` liścia.
- Zaufanie nadaje człowiek (skrypt niczego nie uruchamia, tylko drukuje polecenia): `make trust-ca`. Zestaw:

  ```bash
  # z katalogu repo
  security add-trusted-cert -r trustRoot -p ssl -k "$HOME/Library/Keychains/login.keychain-db" \
    certs/public-ca/ca.crt
  export NODE_EXTRA_CA_CERTS=certs/public-ca/ca.crt   # Claude Code (Node)
  ```

  Polecenie prosi o hasło logowania albo Touch ID. Safari i Chrome czytają pęk kluczy; Node nie, stąd
  `NODE_EXTRA_CA_CERTS` (ustawione w powłoce, z której startuje `claude`). Cofnięcie:
  `security remove-trusted-cert <ca.crt>`. Po restarcie Safari/Chrome (albo nowej karcie) `https://localhost:18745`
  ładuje się bez ostrzeżenia.
- Bez HSTS: HSTS na `localhost` dotyczy wszystkich portów hosta i wymusiłby https także na porcie `:18080` Keycloaka (http, używany przez skrypty).
- TLS 1.2 i 1.3, certyfikat 397 dni (limit Safari); odnowienie: usunąć `certs/proxy` i `certs/public-ca`, `make certs`,
  `docker compose ... restart proxy` (po zmianie CA trzeba ponownie zaufać nowemu `ca.crt`).

### Keycloak na https

Keycloak ma własny port https, `https://localhost:18746` (`KEYCLOAK_TLS_PORT` w `.env`), z certyfikatem z `certs/keycloak`
(to samo CA "dev public", więc `make trust-ca` wystarcza). `KC_HOSTNAME=https://localhost:18746`, więc `iss` tokenów to
`https://localhost:18746/realms/corp`, a ciasteczka `AUTH_SESSION_ID`, `KC_RESTART` i `KC_AUTH_SESSION_HASH` (`Secure;
SameSite=None`) przychodzą z https, które Safari zapisuje. Port http `18080` zostaje dla skryptów (`make token`, admin API w
`kc-sync-bff-client.sh`) i dla ruchu kontenerów: JWKS i token endpoint gateway'a oraz brokera to nadal
`http://keycloak:8080/...`, a `iss` jest tylko porównywany, więc kontenery Java nie potrzebują CA w truststore.

Wybór opcji (a) zamiast "Keycloak za proxy pod prefiksem ścieżki" (b): trasy proxy są w kontrakcie C3 (`/`, `/api`, `/s/`,
`/v/`, `/.well-known/oauth-protected-resource*`), a Keycloak pod prefiksem wymagałby nowej trasy i zmiany tego zestawu;
własny port nie dotyka kontraktu. Wyjątkiem w sieci jest BFF, który do M3 robił discovery pod adresem `iss` (wtedy `idp-relay`, dziś niepotrzebny).

Ciasteczka sesji portalu (`__Host-session`, `SameSite=Lax`) wracają z Keycloaka normalnie, bo callback to nawigacja najwyższego
poziomu.

## Reverse proxy (`proxy/`, usługa `proxy`, profil `m2`)

| Ścieżka | Cel | Uwagi |
| --- | --- | --- |
| `/` | `portal-web:8080` | statyczny serwer SPA (`portal-web/nginx.conf`): fallback na `index.html`, nonce CSP z `$request_id` |
| `/api`, `/api/` | `portal-bff:8080` | callback OIDC BFF: `https://localhost:18745/api/v1/auth/callback` (zarejestrowany w Keycloaku, razem z http `:18740` i `:18090`) |
| `/s/`, `/v/`, `/.well-known/oauth-protected-resource*` | `mcp-gateway:8080` | tylko publiczny listener; `Cookie` usuwany, `Set-Cookie` ukrywany, `nosniff` i CSP `default-src 'none'; sandbox` z `always`, błędy proxy jako JSON |
| `/.well-known/` (reszta), `/admin/v1/` | 404 | JWKS i C5 gateway'a są na osobnym listenerze mTLS (8443), do którego proxy nie ma trasy ani certyfikatu |

Własne strony błędów na trasach gateway'a (także odmowa ścieżki niekanonicznej, 431 dla zbyt dużych nagłówków, 400
dla nieznanego `Transfer-Encoding`) są JSON-em z `nosniff` i CSP; test sprawdza nagłówki, nie tylko status. Access log
ma ścieżki bez query (kody autoryzacji). `;`, `%3b` i każde `%` w ścieżkach `/s/` i `/v/` są odrzucane.

Ścieżki przechodzą dalej bez zmian, więc "normalizacja" to odrzucanie: zakodowane kropki, ukośniki, backslash,
`%25`, `%00`, segmenty `.`/`..` i `//` w części ścieżki dają 404 (wszystkie trasy). `X-Request-Id` nie jest
tworzony ani zmieniany. `Host` i `X-Forwarded-Host` to stały origin publiczny listenera (`localhost:$PROXY_PORT` dla http, `localhost:$PROXY_TLS_PORT` dla https; plik
generowany przy starcie kontenera), `X-Forwarded-For/Port/Proto` ustawia proxy (`https` na listenerze TLS); `Forwarded`, `X-Real-IP`,
`X-Forwarded-Prefix/Ssl/Scheme`, `X-Original-URL` i `X-Rewrite-URL` klienta są usuwane. BFF ufa `X-Forwarded-*` tylko od
adresu proxy (`bff-entrypoint.sh` zamienia `proxy.internal` na regex; po odtworzeniu proxy trzeba zrestartować BFF). Upstreamy są rozwiązywane przy każdym żądaniu: restart gateway'a
albo BFF nie wymaga restartu proxy. Trasy i reguły są w `proxy/routes.conf`, współdzielonym przez oba listenery.

`make proxy-test` (`scripts/proxy-test.sh`, curl): 212 sprawdzeń (w tym listener https z `certs/public-ca`) na zastępczych upstreamach w osobnej sieci
Docker, każda reguła z przypadkiem dodatnim i ujemnym; nie dotyka działającego stosu.

### GitLab jako dostawca OAuth

Klient `mcp-broker`, sekret `GITLAB_OAUTH_CLIENT_SECRET` (`.secrets/dev.env`, także w OpenBao pod
`secret/mcp/oauth-clients/gitlab`, polityka brokera ma tam tylko odczyt). Redirect URI: `${MCP_PORTAL_URL}/api/v1/oauth/callback`
(`http://localhost:18740/...`; dodatkowo `:18090` dla BFF na hoście). PKCE S256 (challenge 43 znaki base64url, verifier 43-128 znaków `[A-Za-z0-9._~-]`) i `state` są wymagane; `scope` jest wymagany
i egzekwowany jak w GitLabie: `api` pisze, `read_api` tylko GET/HEAD (zapis -> 403 `insufficient_scope`), `read_user` tylko
`GET /api/v4/user`, brak lub nieznany zakres w authorize -> `invalid_scope`; powtórne użycie kodu unieważnia wydane z niego tokeny;
dwie metody uwierzytelnienia klienta i powtórzone parametry -> `invalid_request`. Broker prosi o `api` (decyzja
człowieka 2026-10-28), więc zapis przez OAuth (`gitlab__comment_merge_request`) działa; zły klient
albo `redirect_uri` nie przekierowują (400). Kod jest jednorazowy i ważny 120 s; access token żyje
`GITLAB_MOCK_TOKEN_TTL` s (domyślnie 7200, w `.env` można dać 60 do oglądania odświeżenia i zrestartować
`gitlab-mock`); refresh z rotacją (stary access i refresh przestają działać). Stan jest w pamięci: restart mocka
unieważnia wszystkie tokeny.

`/oauth/authorize` bez dodatkowych parametrów pokazuje stronę wyboru konta (alice, bob, carol, mallory) i
"Deny". Wybranie innego konta niż użytkownik portalu jest przyjęte (kontrakty 2.2.3: brak porównania tożsamości; portal pokazuje "połączono jako <backendUser>"). Parametry dopisywane do adresu
w pasku przeglądarki (lub przez skrypt):

| Parametr | Skutek |
| --- | --- |
| `mock_user=<login>` | zatwierdza bez strony wyboru |
| `mock_action=deny` | `error=access_denied` (portal: `cancelled`) |
| `mock_scenario=wrong_state` | w callbacku inny `state` (broker/BFF: `flow_invalid`) |
| `mock_scenario=provider_error` | `error=server_error` zamiast kodu |
| `mock_scenario=token_error` | endpoint `token` odpowiada 500 dla tego kodu |
| `mock_scenario=refresh_revoked` | refresh tego grantu daje `invalid_grant` (połączenie `revoked`) |
| `mock_scenario=short_ttl` | access token żyje 30 s |

## Profil `m2` (`make images-m2`, `make up-m2`)

`make images-m2` buduje z `git archive` HEAD obrazy BFF i web (repo `mcp-portal`) oraz czterech serwerów ws-04
(`ONLY=web,gitlab` ogranicza zestaw); tagi `m2-<sha>` trafiają do `.env`. `make up-m2` robi `up -d --wait` profili
`full` i `m2`: Compose odtwarza tylko usługi, których konfiguracja albo obraz się zmieniły (lista z
`docker compose ... up -d --dry-run`), po czym `make m2-sync` stosuje to, co leży poza definicją kontenerów:
klient `mcp-portal-bff` w działającym Keycloaku (z `keycloak/realm-corp.json`), ACL Redisa (`redis/*.rules`) i restart
proxy. Brokera, gateway i serwery MCP mają healthchecki (gateway: odpowiedź listenera publicznego; broker i serwery:
przyjęte połączenie TCP na 8443, bo Tomcat otwiera konektory na końcu), więc `--wait` czeka na gotowość.

Gateway: obraz `mcp-gateway:m2-d65088f`, `MCP_PUBLIC_URL=https://localhost:18745` (proxy; `resource` w metadanych RFC 9728
jest adresem proxy), cztery serwery ws-04 pod `MCP_SERVER_<SYSTEM>_MCP_URL`, C5 pod aliasem `mcp-gateway.internal:8443`
(stuby C4/C5 są zatrzymane), certyfikat `mcp-portal-bff` dla BFF, `MCP_ADMIN_AUTHORIZED_PARTY=mcp-portal-bff`. Port
18000 gateway'a zostaje tylko dla `make m1` (scenariusze mcp-e2e łączą się wprost z `127.0.0.1:18000`); klienci używają
proxy. Broker: `mcp-credential-broker:m2-bcfec7a`, sekret klienta GitLaba czytany z OpenBao (`secret/mcp/oauth-clients/gitlab`, polityka
tylko na tę ścieżkę), bez zmiennej środowiskowej.

BFF (od M3) działa w sieci `core` z aliasem `portal-bff.internal` i konfiguracją OIDC bez discovery (`PORTAL_OIDC_AUTHORIZATION_URI` na adres publiczny, token, JWKS i wylogowanie przez `http://keycloak:8080`); `idp-relay` i truststore w BFF usunięto. Wcześniej: alias sieciowy BFF (`portal-bff.internal`)
należy do relay. Wylogowanie z IdP (`end_session_endpoint`) działa tak, jak zwraca je Keycloak.

Serwery mają `MCP_<SYSTEM>_ALLOW_PLAIN_HTTP=true` (mocki po http), `MCP_CONNECT_URL=https://localhost:18745/connections?system={system}`,
własne certyfikaty i użytkowników Redisa. Service desk: `MCP_SERVICEDESK_CREDENTIAL_MODE=service-account`, kolejki `IT`.

Czego jeszcze nie ma w tym stosie: poświadczenie `service-account` service desku w brokerze (klucz: `SERVICEDESK_API_KEY`),
`token-exchange` OpenSearch w brokerze.

## `make m2`

Scenariusz demo na działającym stosie `make up-m2`: mocki (whoami, brak passthrough, REST), przepływ OAuth z mockiem,
prawdziwy broker (`oauth/start` -> authorize -> `oauth/complete`, zły `state`, odmowa, rozłączenie), ACL Redisa
(`portal-bff` bez FLUSHALL/KEYS/SCAN/SCRIPT/FUNCTION/MIGRATE i bez kluczy `gw:*`, broker: skrypt tylko na swoich
kluczach), Keycloak, proxy oraz portal przez proxy: logowanie OIDC alice, `me`, katalog, zapis PAT Jiry, "Połącz przez
OAuth" (GitLab) z odmową i odłączeniem, link utworzony w portalu, klient MCP (`initialize`, `tools/list`, `tools/call`)
przez `/v/<slug>/mcp` z metadanymi RFC 9728 na adresie proxy, `credential_required` z linkiem do portalu, usunięcie
linku, wylogowanie. Przebieg używa użytkownika alice i sprząta to, co utworzył (link, połączenie GitLab); PAT Jiry
alice jest zapisany ponownie tą samą wartością. Pozostają 2 SKIP: interfejs web w przeglądarce (brak sterownika
przeglądarki) i Claude Code (wymaga człowieka).
