# M6 environment, stages 1 and 3

Items 1 to 6 are stage 1, items 7 to 10 are image rollouts (stage 3 starts at item 9). `make layers` shows the active image layer.

Cleanup after M5 in `mcp-platform-dev`: the stack coming back after Stop and Start, `make smoke` on a real broker, CI runner isolation,
two optional profiles for mcp-e2e (a server with 250 tools, and a production-mode gateway) and housekeeping. The default stack does not change: both profiles are separate compose files that
`scripts/compose.sh` does not read.

## 1. Stop and Start without manual help

Cause: the broker, the MCP servers and `registry` depended on one-shot tasks (`openbao-init`, `server-state-init`, `registry-data-init`) with the condition
`service_completed_successfully`. `docker compose start` and the Start button in Docker Desktop create nothing, so when a task container was gone
(`run --rm`, Docker cleanup), they failed with "is missing dependency". When the container existed, `start` ran the task again (measured
on a one-off project: two runs per Stop and Start).

Changes:

- dependencies on these three tasks have `required: false`: a missing container is a warning, not an error; `up` still runs the task and waits for it.
  Note: with `required: false` a service that depends on a failed task starts anyway (measured), so the `make up*` targets record the time before `up`, and after a failed `up --wait` they call
  `scripts/init-failed.sh TIME`, which counts only tasks that failed after that time (an old `exited N` container means nothing), only from the profiles of the target, and stops only the dependent
  services started after that time; services that were running earlier stay untouched (also when a repeated task fails briefly). `make` ends with an error. The test in `start-test`
  (8 checks): a fresh failed task stops the dependent service, an old `exited 7` does not stop a running one, a failed repeat of a task does not touch a service that was running earlier. A plain `compose start` without the task stays
  allowed (the stack after Stop should come up, the task already succeeded once);
- after success `scripts/wait-init.sh` removes the finished containers of these tasks (`docker rm` only for the state `exited 0`), so Start does not repeat them
  and `openbao-init` does not touch OpenBao at Start. OpenBao data (raft on the volume `openbao-data`) and `openbao-unseal` (restart `unless-stopped`) are unchanged;
- `make start-test` (`scripts/start-test.sh`, the step `start` in `make ci`): its own one-off project `mcp-dev-starttest`, without the ports and volumes of the stack: `up`,
  `stop`, removing the task container, `start` (the service comes up, the task is gone), a second Stop and Start; 4 checks;
- `scripts/check-compose.py`: no service requires the task container to exist (in all three layers).

Proof on a running stack (without stopping anything): the task containers removed by `wait-init.sh`, then `docker compose ... start` of the whole project
(`--profile full --profile m2 --profile ci`) passes with only the warnings "is missing dependency ..." and code 0; before it ended with an error
on `registry`. `up --dry-run` recreates no service (a dependency change does not change the configuration hash), it would run only the three tasks.
A full Stop and Start of the whole stack was NOT done (rule: at most once, after confirming OpenBao persistence in the logs).

## 3. CI runner isolation and `ci-main`

In the repository (the settings on the CI platform side listed below are done by a human):

- `.github/workflows/ci.yml`: the job with the Docker socket (`docker-tests`) has `environment: ci-main`; the Environment `ci-main` must have
  Settings > Environments > ci-main > "Deployment branches and tags" set to "Selected branches": `main`. Without it a branch could put
  the same environment into its own copy of the file. The `checkout` action is pinned to a SHA as in the server repositories;
- `.gitlab-ci.yml`: the job with the tag `docker-socket` only for the default branch and not for a merge request pipeline; the tag must belong to a protected
  runner (Settings > CI/CD > Runners > "Protected"), and then the runner will not pick up a pipeline of an unprotected branch;
- `Jenkinsfile`: the stage with the socket has `when { beforeAgent true; branch 'main' }` (without it Jenkins would take the `docker` node for other branches too); the `static` stage on a pool labeled `ci-style` (no socket), the stage with the socket on the `docker` node (`main` only, a one-off agent: recreated after
  every build, because the socket gives its holder the whole daemon); the `Jenkinsfile` for pull requests must come from a trusted branch;
- `ci/local-runner.sh` (local runner): an unprivileged runner container (`--cap-drop ALL`, `no-new-privileges`, a process limit); the Docker socket stays, so
  the runner is only for this repository's code. Checked: `make ci-local JOB=static` passes with these options; the `docker-tests` job with the socket
  was not run again (that is a `make ci` step for the coordinator).

## 4. Server with 250 tools (profile `bulk`)

The contracts know five systems (`SystemId` and `ServerId` in `common.schema.json`, `ServerRegistry.SYSTEMS` in the gateway, `Scopes` and `Refs` in the Cedar schema,
`EndpointFilter`). An `mcp-bulk` with its own system `bulk` and group `mcp-bulk-read` is therefore a contract change, not an environment task: the manifest
would be rejected at registration, and the gateway would not start with such a server in its configuration. This was not worked around. Instead the stand-in takes the identity
of an existing system whose group and policy rules already exist: **`mcp-confluence`** (group `mcp-confluence-read`, rule `confluence-call-read`).

- `mocks/mcp/mcp_stub.py` (set `bulk`): 250 tools `read_item_001..250`, `READ_ONLY`, closed schemas; mTLS (client CN `mcp-gateway`), the internal JWT checked
  in full (ES256 in pure Python, the 59 vectors of `mcp-contracts/test-vectors/jwt` give the same denial reasons), `GET /mcp-manifest`, a definition hash matching the contract
  (the `definition-hash` vectors and the hashes of the four real Confluence tools from the build artifact). The manifest contains the four real tools unchanged
  (`MCP_STUB_BASE_MANIFEST`: the artifact `mcp-server-confluence/mcp-app/target/mcp-manifest.json`), so their approvals in the registry (also `create_page`, UPDATE)
  survive the switch in both directions; for the duration of the test they answer with a fixed text.
- The list for a reader (`mcp-confluence-read`): 3 real READ_ONLY tools + 250 = **253** in pages of 100, 100, 53. The "bulk" account in e2e also sees the tools of its other groups
  (today 8 from Jira and OpenSearch in `FULL_GROUPS`), so the expected total in the 250-tool test is 8 + 253 if it also gets `mcp-confluence-read`.
- The filter in e2e is `systems=confluence` (not `bulk`); the names are `confluence__read_item_NNN`.
- A fix after review: the stand-in tool hashes are computed from the credential of the base manifest (earlier from the stub settings, so 250 hashes did not match and registration would fail), the same script
  `scripts/stub-manifest.py` generates the manifest for `bulk.sh` and `e2e-prod.sh`, and checks every hash before printing. `bulk.sh on` registers the manifest BEFORE removing the real server
  (a registry refusal changes nothing), `on` and `off` are idempotent (they always register and check the list), and the trap prints the way back.
  The tools of the real server on the stand-in return `isError`, not success. After an interruption: run `scripts/bulk.sh off --confirm` again; when no `mcp-confluence` is running: `make up-m2`; when the registry has a manifest with 254 tools and the real server is running: `make registry-register SERVERS=mcp-confluence`.
  `make up*` refuses (`scripts/bulk-guard.sh`, the first precondition, before removing the gateway) when the stand-in exists.
- On the main stack (it changes it for the duration of the test, only on the coordinator's order): `make bulk-on` (without `CONFIRM=1` checks and a plan), `make bulk-on CONFIRM=1`,

  one-off user sees 253 tools. `bulk-off`: the reverse, with the real server manifest from `../mcp-server-confluence/mcp-app/target/mcp-manifest.json`.
  While the stand-in exists, `scripts/compose.sh` refuses every `up` (the real server would come up next to it under the same address). The real container is removed during that time,
  not only stopped, so that Start in Docker Desktop does not bring both up at once.
  Checked without changing the stack: `compose up --dry-run` of both overlays, `bulk.sh on` without `--confirm` (checks and a plan). The whole `on` and `off` run step by step (registration

| --- | --- |
| `gateway` | the stack's gateway image (`MCP_GATEWAY_IMAGE`), WITHOUT the `devstack` profile and without acknowledgements; its own PostgreSQL, Redis with a replica (`WAIT` required outside dev), internal JWT keys `stack-c2-*` from `out/e2e-prod/c2-jwks.json`, the stack's policy bundle re-signed with the key `e2e-prod-main` (not `dev-`, not `test-`) |

| `mcp-jira` | a stand-in of the `xh` set (one tool `search_issues`, credential `user-secret`) under the identity `mcp-jira` |
| `mcp-confluence` | a stand-in of the `bulk` set as above (the 250-tool test outside the main stack) |
| `postgres`, `redis`, `redis-replica`, `policies`, `idp-front` | backing services |

Addresses (127.0.0.1, `e2e-prod.env`): public gateway `http://localhost:18760/mcp`, gateway admin over mTLS `https://localhost:18761` (TLS name `mcp-gateway.internal`), broker admin `http://localhost:18762`.

## 8. Stand-in response time (tools/list with many parallel lists)

Measured in a `python:3.12-alpine` container: ES256 verification of one token takes 13.8 ms in pure Python with affine addition, and 2.7 ms after moving to Jacobian coordinates with one shared
doubling chain (Shamir's trick) and one inversion; the `jwt` vectors give the same denial reasons (59 in the tests). In addition `VerifiedTokens`: a token signature checked once is skipped when the same token
is reused until its `exp` (key: the full token and the key point); claims, `jti` replay, the variant, the tool and `X-Request-Id` are checked every time. Socket backlog 512 (default 5), compact serialization,
handling time in the stand-in log (`handled ... in N ms`). With 60 parallel lists, 179 requests to the stand-in: median 61 ms, maximum 134 ms, TLS handshakes at most 98 ms.

The gateway reports `left out of the list (timeout)` remain with 20 or more parallel lists after its definition cache expires (up to 60 s): 160 of 180 requests reach the stand-in in the first second
and are handled in about 60 ms, and the delayed ones are requests the gateway sends later. One list page costs the gateway about 1 s of CPU even without load (authorizing 253 tools), so 60 parallel lists mean about 60 s of CPU
on 12 cores, and the limit `MCP_TOOLS_LIST_TIMEOUT` (3 s) counts time waiting for gateway CPU. This is gateway behavior (mcp-gateway), not the stand-in: an older stand-in version gave the same result (47-59 of 60 with 60 parallel).
Up to 10 parallel lists: 0 omissions; 200 lists in a row on e2e-prod: 0 omissions and 0 `left out` entries in the gateway log.

V10 guard: after the rollout `apply-m6c-switch.sh` writes the marker `out/m6c.applied` (outside git). `scripts/compose.sh` refuses `up`, `create` and `run` (code 5) when `M6C_ACTIVE` is not 1 and the marker exists or

Version probes in the mocks versus production. The OpenSearch mock answers `GET /` anonymously, and a cluster with the Security plugin usually requires authentication: the `mcp-opensearch` probe then gets 401 and the state `degraded` without a version
(`list_indices`, `validate_query` and `get_cluster_health` refuse). On such a cluster, if it is OpenSearch 2.x or 3.x, `MCP_OPENSEARCH_ASSUME_TESTED_VERSION=true` must be set (on 401 or 403 the state is `supported` with the version
`unknown`; another distribution is still `degraded`); this is an operator's declaration, not a reading. A question for the server owners: should the OpenSearch probe use a credential (a postponed contract change request), so that production does not depend on this flag.
