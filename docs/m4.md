# M4 environment

Migration of the environment to mcp-contracts 4.0.0 (CHANGELOG 4.0.0, "mcp-platform-dev"). Everything below is in the repository and works on the
M3 stack as preparation; activation is one command, `make m4-switch`, run on the coordinator's order when the images of the
M4 components are ready. Tests: `make m4` (stack), `make m4-test` (unit, no stack), `make openbao-test` (isolated OpenBao).

## Registry pipeline certificates: one per server

`make certs` issues `certs/mcp-registry-ci-<serverId>` for `mcp-jira`, `mcp-confluence`, `mcp-gitlab`, `mcp-servicedesk`,
`mcp-opensearch` (CN exactly `mcp-registry-ci-<serverId>`, EKU clientAuth). The shared M3 certificate `mcp-registry-ci` was
removed from the stack; its copy with the same CN is in `certs/legacy/mcp-registry-ci` only for the test that gateway 4.0.0 answers
`403` to it. The `mcp-offboarding` certificate (clientAuth) has existed since M3. All private keys and keystores in `certs/` have mode 600 (`make m4` checks all of them).

`make registry-register` plays the pipeline role of each server: `PUT /admin/v1/registry/servers/<serverId>` (gateway admin API, listener
`https://localhost:18445`, mTLS) with the certificate of that server and a manifest built from code, that is `mcp-app/target/mcp-manifest.json` from the
repository `../mcp-server-<name>` (or `MANIFEST_DIR/<serverId>.json`). It never sends a manifest fetched from a running
server.

Differences between dev and production:

| | production | this stack (dev) |
| --- | --- | --- |
| where the registry manifest comes from | only a `PUT` from the protected-branch pipeline, a foreign CN gets 403 | `PUT` as in production (`make registry-register`), plus bootstrap |
| bootstrap (the gateway fetches the manifest from the server) | does not exist | yes, only when the gateway has the `devstack` profile (`MCP_REGISTRY_BOOTSTRAP=true`); rows have `source=bootstrap` |
| tool approval | `READ_ONLY` from `PUT` automatically, `UPDATE` and `DESTRUCTIVE` through an administrator `approve` | the same for rows from `PUT`; a bootstrap manifest is not approved outside dev mode |
| `make registry-refresh` | does not exist | deletes only `bootstrap` rows and restarts the gateway (after a tool definition changes); it does not touch `ci` rows |

In M4 the stack has both paths, but `m4-switch` starts by deleting the `bootstrap` rows and registers everything through `PUT`, so entries have
`source=ci`. After a tool definition changes in dev: build the server, run `make registry-register`, and approve the `UPDATE` and `DESTRUCTIVE` tools
in the portal.

## `dev-` keys

The stack used the published keys `test-policies-{main,overrides}-dev`. Since M4 the 4.0.0 bundles of the policies repo are signed with the keys
`dev-policies-main` and `dev-policies-overrides` (public: `../mcp-policies/keys/dev/`; the policies repo generates and keeps the keys, this repo does not duplicate them).
Compose takes the identifiers from `.env` (`POLICY_KEY_MAIN_ID`, `POLICY_KEY_OVERRIDES_ID`, directory `POLICY_KEYS_DIR`), by default still `test-`, so just
introducing the variables does not change the running configuration (the effective `compose config` is identical). `make m4-switch` sets `dev-`.
Recipients accept `dev-` only in dev mode (the `devstack` profile plus explicit acknowledgements, which compose already sets; `allowTestKeys` from the policies repo channel).
`make m4` checks that the signature of the latest `main` bundle matches the key the gateway gets. The gateway JWT keys are ephemeral, so there is
nothing to switch for the JWT.

## Token exchange to OpenSearch (RFC 8693)

The realm has had this since M1: the client `mcp-credential-broker` has `standard.token.exchange.enabled`, an optional scope `opensearch-audience`
(mapper `aud=opensearch`), and the gateway and BFF cannot exchange for this `aud` (HTTP 400). The OpenSearch mock accepts a Bearer with
the Keycloak `iss` and an `aud` containing `opensearch`; a token with `aud=mcp-gateway`, `aud=mcp-credential-broker`, a PAT or no token gives 401, and
`hr-*` and `logs-team-b-*` by name give 403. No changes to the realm or the mock were needed. `make m4` runs the whole chain as alice and bob:
client token -> `aud=mcp-credential-broker` (as the gateway) -> `aud=opensearch` (as the broker), checking `sub`, `azp`, `exp` (the contract requires
`expiresAt`; the token expires after 900 s) and calling the mock. The mock does not verify the JWT signature (see STATUS, M2).

## Service Desk service account

`openbao/init.sh` writes `secret/data/mcp/service-accounts/servicedesk` with the field `value` (the value of `SERVICEDESK_API_KEY` from
`.secrets/dev.env`, generated, not in the repo; the mock accepts the same key; the broker reads `value` for Bearer, `username` and `password` for Basic, optionally `expires_at`, and takes the scheme from the system configuration, `SECRETSCHEME=Bearer`). The broker AppRole policy got
`read` on `secret/data/mcp/service-accounts/*` (no write, delete or list). The field layout was agreed with the broker owners (the contract gives only the path). Also added is `secret/mcp/oauth-clients/opensearch` (the broker's exchange client, the `client_secret` of the Keycloak client); the broker policy reads `oauth-clients/*`. The Service Desk mock
accepts the key as `Bearer`, `ApiKey` or `Token`; a Keycloak JWT, a PAT or no credential gives 401, so a leak of a user token
to this system shows in the mock journal (`make mock-auth SYSTEM=servicedesk`, row `auth: jwt`). The write to the running OpenBao
happens at the switch (`openbao-init` is one-shot); `make openbao-test` checks the same script on a temporary OpenBao.

## Offboarding

```bash
make offboard USER=<login> DRY=1     # plan only: IdP groups and sub
make offboard USER=<login>
```

Order (`scripts/mcpdev.py offboard`): the IdP (remove the user from all groups, end sessions, which triggers the portal's back-channel
logout), `POST /v1/admin/users/{sub}/purge` on the broker, `POST /admin/v1/users/{sub}/purge` on the gateway, both with the `mcp-offboarding`
certificate and no token, and then both purges once more (a contract recommendation: an open OAuth flow could have created a connection after the
first one). Each call is independent: a failure of one does not stop the rest, but the exit code is 1. `sub` is the user's `id` in Keycloak.
Activity in the portal table stays until the end of retention, and an MCP client token issued before `purge` works for up to 60 min (a window accepted
by a human). The accounts `alice`, `bob`, `carol`, `mallory` are shared, so `offboard` refuses them without `--allow-shared`
(the `DRY=1` plan is allowed). For tests `make m4` creates a one-off user `m4-<random>` and deletes it at the end.

## Identity governance (IGA)

The `mock` adapter runs inside the BFF process (`PORTAL_IGA_ADAPTER=mock` in the `dev` profile, data from `PORTAL_IGA_MOCK_FILE=/dev-data/iga-mock.yaml`,
the directory `../mcp-portal/bff/dev` is mounted into the container); compose already has this. The portal migration to 4.0.0 (`503`/`422`/request idempotency,
`GET .../entitlements`) does not need a separate service, so no IGA service was added. The requester identity stays the claim
`preferred_username` (`PORTAL_IGA_REQUESTER_ID_CLAIM`, the default).

## Switching: `make m4-switch`

`make m4-switch CHECK=1` only checks preconditions and changes nothing: the images from `.env` exist and are not `m1-`..`m3-` images, the `dev-` keys exist,
every server has a manifest to `PUT`. `make m4-switch` does the following in order (PostgreSQL, Redis and OpenBao state and Authenticator registrations stay):

1. `.env`: the policy key identifiers become `dev-policies-main` and `dev-policies-overrides`,
2. `openbao-init` (service account, broker policy) and `scripts/redis-sync-acl.sh`,
3. the broker, then five MCP servers (they declare `environment: dev`); the OpenSearch server with `acceptedTypes` containing `token-exchange` must be
   ready before the gateway (otherwise the gateway disables it at startup),
4. delete the registry `bootstrap` rows, the gateway, `make registry-register` (CI certificates),
5. BFF and web, proxy restart,
6. a signal to the policies repo (a message in the output) and waiting up to 10 min until a published `main` bundle verifies with the `dev-` key (the policies repo runs
   `.ci/switch-stack.sh --confirm` in `mcp-policies`; `M4_PUBLISHED=1` skips the wait); until then the 4.0.0 components have no bundle they would accept,
7. `proxy-test` and `make m4`.

The 4.0.0 bundles come from the policies repo channel (`out/repository-m4/`, published to `out/repository` by that repo, with no return to 3.1.x); an old 3.1.x bundle
would be rejected (`schema_mismatch`). Rollback is not automatic: the images from before the switch are in
`out/m4-previous-images.txt`, but the gateway remembers the accepted bundle revision (rollback protection), and the registry has entries from `PUT`.

## `make m4`

Part one works on any stack and changes nothing: CI certificates (CN, EKU, CA, mode 600), the `dev-` keys, the signature of the latest bundle, token exchange and the
OpenSearch mock, the service account and the Service Desk mock, the OpenBao policy. Part two is SKIP with the reason "before the switch" until the running
gateway and broker are `m4-` images: a foreign server certificate and the old CN (403) and one's own (200), offboarding (groups disappear from the token,
both `purge` calls 204 and the `user_purged` event, a foreign certificate 403, an unknown `sub` 204), `429` with `Retry-After`, the service account visible in the mock journal
as a key, not a JWT. Two steps have no executor on this stack: `environment=dev` rejected without dev mode needs a second gateway without the `devstack`
profile (the stack deliberately runs in dev mode), so it stays a SKIP with that reason; the `429` limit is a SKIP if 400 requests did not trigger
a response (limit not configured). Part two was written against the 4.0.0 contracts and has not been run on real M4 components.

## The M4 layer in compose

`docker-compose.m4.yml` and `m4.env` are included by `scripts/compose.sh` only with `M4_ACTIVE=1` (`make m4-switch` writes it to `.env` after
checking the preconditions). They contain the broker image `m4-9fb07d2`, the `dev-` policy key identifiers, the `devstack` profile with `MCP_ALLOW_TEST_KEYS=true` for the broker
(both acknowledgements, as the broker README requires), and the broker systems `opensearch` (`token-exchange`, client `mcp-credential-broker`, audience `opensearch`,
scope `opensearch-audience`) and `servicedesk` (`generic-rest`, `service-account`, `SECRETSCHEME=Bearer`). The images of the other components
are added to `m4.env` when ready. After the switch `make m4` also checks `resolve` through the gateway for OpenSearch (JWT `aud=opensearch` in the mock journal) and for Service Desk (a key, not a JWT).

## Dev groups for Service Desk and OpenSearch

The realm (`keycloak/realm-corp.json`) gives `alice` the groups `mcp-servicedesk-read`, `mcp-servicedesk-write` and `mcp-servicedesk-queue-IT`, and `bob` the groups
`mcp-servicedesk-read` and `mcp-servicedesk-queue-FIN` (a new group, matching `ServiceDesk::Queue/FIN` from `mcp-policies/entities/static.json`). The HR queue has no group, so it is
out of scope for everyone. OpenSearch was already granted: `alice` and `bob` have `mcp-opensearch-read` and `mcp-opensearch-idx-logs-team-a` (`logs-team-b` and `hr-*` nobody),
which matches `static.json`, so e2e can call OpenSearch without changes. The realm import runs only when the container is created, which is why `make m4-switch` calls
`scripts/mcpdev.py sync-groups`: it adds the missing groups and memberships from the file to the running realm (add only, no removal; Keycloak sessions stay).
New groups reach tokens from the next login. `make m4` checks the groups (before the switch a SKIP with the list of missing ones) and, after the switch, the queue scopes through the gateway.
