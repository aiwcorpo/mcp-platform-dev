# M5 environment

Preparation of the environment for mcp-contracts 5.1.0 (CHANGELOG 5.1.0, section "dev stack"; items A, B, C and E of the M5 plan). Everything below is
in the repository. The M4 stack at `https://localhost:18745` keeps running unchanged: the M5 layer is ignored until `.env` has `M5_ACTIVE=1`,
and only `make m5-switch` sets it, run on the coordinator's order with human consent. The preparation restarted nothing.

## What the M5 layer contains

`scripts/compose.sh` adds `docker-compose.m5.yml` and `m5.env` on top of the M4 layer (the M5 layer alone, without M4, is rejected).

| Service | Role | Host port | Notes |
| --- | --- | --- | --- |
| `mcp-gateway` | gateway, instance 1 | 18752 (public listener) | state volume `gateway-state`; loses the alias `mcp-gateway.internal` |
| `mcp-gateway-2` | gateway, instance 2 | 18753 | same image and environment (checked by `scripts/check-compose.py`), separate volume `gateway-state-2`, starts after instance 1 (Flyway migrations) |
| `gateway-lb` | load balancer in front of the gateway (nginx) | 18000, 18445 (addresses from before M5), 18750 (status) | `mcp-gateway.internal` is an alias of the balancer; :8080 http, :8443 mTLS as TCP passthrough |
| `mcp-credential-broker`, `mcp-credential-broker-2` | broker, two instances | 18754, 18755 | one database and one Redis; M4 settings duplicated in the layer for instance 2 (a test compares the environments) |
| `broker-lb` | load balancer in front of the broker | 18100 (address from before M5), 18751 (status) | `mcp-credential-broker.internal` is an alias of the balancer; mTLS passed through unchanged, so the client CN reaches the broker |
| `proxy` | nginx in front of the portal and gateway | unchanged (18740, 18745) | mounts `proxy/m5/*`: the exact route `/mcp` and `/.well-known/oauth-protected-resource/mcp` with `nosniff` and CSP, upstream `gateway-lb:8080`; `/v/` without an upstream: `404 not_found_or_denied` from the vector `legacy-link-route-gone` (JSON, nosniff, CSP); 8192 connections per worker so the proxy is not the bottleneck of the load test |
| `packages`, `registry` | package server and image registry, profile `ci` | 18756, 18757 | separate network `ci`, no access to the stack network; `make m5-artifacts` starts only these two services (and the one-shot `registry-data-init`, which gives the volume uid 65534). Registry: user `nobody`, read-only file system, `cap_drop ALL`, deletion through the API disabled (`DELETE` gives 405; the image enables it by default, so the setting is explicit) |

Redis and PostgreSQL stay a single instance shared by both instances (in dev this is a deliberate point of failure; HA of Redis itself
and of the database is the operator's topic, M6). The gateway gets `MCP_TOOLS_LIST_TIMEOUT` (m5.env, 3000 ms) and a shared private JWKS of the internal JWT key
(`MCP_INTERNAL_JWT_KEYS_FILE`, `MCP_INTERNAL_JWT_ACTIVE_KID=stack-c2-1`; `make c2-keys` generates `.secrets/c2-jwks.json`). Without a shared file
each instance draws its own keys, and a recipient that validated a token from instance A rejects a token from instance B until it fetches the JWKS again.
The cursor keys `MCP_ACTIVITY_CURSOR_KEY` and `MCP_LIST_CURSOR_KEY` (a secret from `make secrets`, the same on both instances; `check-compose.py` checks equality and length) are shared, because a cursor issued by one instance is read by the other. The gateway's Redis ACL has `+wait` (`redis/gateway.rules`; applied by `redis-sync-acl.sh` during the switch); `MCP_REDIS_WAIT_REPLICAS` stays at the default (one Redis, no replica). The file format (a JWKS with P-256 private keys, `kid` without
the prefixes `test-` and `dev-`) comes from `SigningKeys.java`. Checked on the real image `mcp-gateway:m5-2f3c4a4`: started in an isolated network with this file, the cursor keys and the stack configuration, it passed key loading and the devstack guard without an error and without a warning about generating its own keys (it stopped only at fetching the policy bundle, because it had no network).

### Load balancers (`lb/`)

nginx (an image already used in the stack, no new pulls). Instances are found through the alias `gateway-backends.internal` /
`broker-backends.internal`, which every running instance carries; the address is resolved every second (Docker DNS), so a stopped
instance disappears, and a recreated one (even with a different address) returns without restarting the balancer. Consequences, checked by `make lb-test`:

- no active health checks (nginx OSS): a dead address is skipped after a failed connection and the request goes to the next instance,
  with no error for the client (test: 60 http requests, 40 gateway TCP and 40 broker TCP connections after `docker kill` of one instance, zero errors);
- a request that reached an instance is not retried (POST): killing an instance during a call ends that call with a 502 error,
  and the client retries. This is deliberate: retrying `tools/call` could run the action a second time;
- no sticky sessions: MCP sessions and TOTP confirmations must live in Redis. If the gateway owners decide otherwise, a hash on
  `Mcp-Session-Id` in `lb/gateway.conf` is enough; today it is off so that the test "a TOTP started on one instance finishes on the other" is honest;
- the mTLS listener (:8443) is only passed through (the `stream` module), so client certificates (`mcp-registry-ci-*`, `mcp-offboarding`, BFF)
  and the gateway JWKS work as before M5; the balancer sees nothing of the request;
- the balancer access log has the path without the query, `X-Request-Id` and the instance address; the nginx error log (level `error`) describes a failed request together with the query, that is with the `/mcp` filter (system and tool names, no secrets or authorization codes);
- the balancer's own errors (400, 413, 414, 431, 494, 502, 503, 504) are JSON (`invalid_request` or `upstream_unavailable`), not an nginx page; a header up to 16 KB passes (cookies), and instance errors pass unchanged.

HAProxy was not used: the image is not in the stack, and pulling a foreign image needs human consent. If active
health checks are needed, the change affects only two files in `lb/` and two services in the layer.

### Memory (after the load tests, 2026-11-01)

The gateway (both instances) and the five MCP servers have `mem_limit: 2g` in the M5 layer. The five servers get `JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=70 -XX:+ExitOnOutOfMemoryError`; the gateway gets nothing
(since M6: the gateway image has its own `-XX:MaxRAMPercentage` and `-XX:+ExitOnOutOfMemoryError` in `ENTRYPOINT`, and command-line flags win over `JAVA_TOOL_OPTIONS`, so the 70% entry was dead; the gateway heap is 75%: that is what the `ENTRYPOINT` of the image `m5-b2e25ae` has (checked with `docker image inspect`); 60% appears only in a newer Dockerfile whose image was not built). The heap fits in the limit, and running out of memory ends the JVM
with its own error (the container starts again, the cause is in the log) instead of `exit 137` from the kernel. Earlier the JVM took a quarter of the Docker machine memory (gateway-2 held 4.1 GiB). The new gateway variable
`MCP_AUDIT_THROTTLE_MAX_TARGETS_PER_USER` (default 50) is in the layer. The gateway image: `m5-b2e25ae`. One instance at a time was recreated (gateway 1, gateway 2, jira, then confluence, gitlab, servicedesk, opensearch); all servers have the limit.
Optional gateway overload settings (not set in the layer, defaults apply): `MCP_MAX_CONCURRENT_REQUESTS` (MCP requests in flight per instance, default 128), `MCP_CONCURRENCY_QUEUE_WAIT` (100 ms of waiting for a slot) and
`MCP_SHED_RETRY_AFTER_SECONDS` (the `Retry-After` of a 503 refusal, 2 s); request limits in a window: `MCP_RATE_LIMIT_*` (gateway README, section "Overload"). In a load test tune them in `docker-compose.m5.yml` together with `mem_limit`.

## The switch (`make m5-switch CONFIRM=1`)

`make m5-switch CHECK=1` only checks the preconditions. The switch itself requires `CONFIRM=1` (`--confirm`) and the coordinator's order.

Before the first change the script makes a backup in `out/m5-backup-<UTC time>/` (every run has its own directory, a rerun overwrites nothing): full dumps of the
`gateway` and `broker` databases (schema and data, `pg_dump --clean`), a separate dump of `virtual_servers` (DDL and data), Flyway versions, the running images, `.env`, the revision of
the latest policy bundle and the connection counts of the broker for the accounts alice, bob, carol, mallory (system and state, no content). The switch state is in `out/m5-switch.state`;
for an unfinished switch the next run refuses unless `RESUME=1` (it uses the same backup).

Order: backup -> `openbao-init` (a new broker `secret_id`, see below) -> internal JWT keys -> Redis ACL (`+wait`) -> `M5_ACTIVE=1` in `.env` -> broker 1, broker 2, `broker-lb` ->
signal to the policies repo and waiting for a bundle whose manifest has `schemaVersion` 5.x (new revision and dev- signature checked separately) -> MCP servers -> gateway 1, the `/app/state` state
copied to the volume of instance 2 (so that rollback protection of bundles works from the start), gateway 2, `gateway-lb` -> manifest registration by CI -> BFF and web -> proxy
-> restart of the Confluence, Service Desk and OpenSearch mocks -> checks. The checks whose result counts in the exit code: the instances (devstack profile, shared internal JWT keys, `/mcp` metadata on both),
`proxy-test`, `make m4`, `/mcp` through the public address `https://localhost:18745` (the 401 challenge with metadata without a query, `/v/` as 404 `not_found_or_denied`) and a comparison of the connection counts
of the four accounts before and after. Any failure gives a nonzero code and a rollback hint; the stack stays as it is. Not touched: Keycloak, PostgreSQL (apart from component migrations),
Redis (AOF volume), OpenBao (apart from renewing `secret_id`; since `make openbao-migrate` with a persistent volume), the bundle server, Authenticator registrations, the Jira mock and the GitLab mock (the latter only with `RESTART_GITLAB_MOCK=1`;
it keeps OAuth tokens in memory, so GitLab connections must then be made again).

Unavailability: the broker (tens of seconds to two minutes, including waiting for the bundle if the policies repo publishes only after the signal), then the MCP servers
and the gateway. People using the M4 stack will see errors during this time; the switch is not zero-downtime.

### Failure during the switch and rollback

Every error after the backup ends with a message naming the step, the command that failed, and the command `scripts/rollback-m5.sh out/m5-backup-<time>` (or `RESUME=1` after fixing the cause).
`make m5-rollback BACKUP=... CONFIRM=1` (without `CONFIRM` only a plan):

1. removes `gateway-lb`, `broker-lb`, `mcp-gateway-2` and `mcp-credential-broker-2` (they hold ports 18000, 18445, 18100 and the TLS aliases, which would otherwise be doubled in DNS);
2. stops the M5 gateway and broker;
3. restores the `gateway` and `broker` databases from the dumps in one transaction (this reverts V7, which drops `virtual_servers`, and the V7 entry in the Flyway history; whatever the components wrote to these two databases since the backup is lost;
   `SKIP_DB=1` when the switch failed before any M5 component ran a migration);
4. removes `M5_ACTIVE` from `.env`;
5. waits for a 4.x bundle (gateway 4.x and M4 servers reject a 5.x bundle: the policies repo publishes the 4.x bundle again, the signal is printed);
6. recreates from the `m4.env` images: broker, servers, gateway, BFF, web, proxy.

It does not revert: MCP sessions created by the M5 gateway in Redis (gateway 4.x answers 404, the client runs `initialize`), tables created only by M5 migrations (they stay unused), the volume `gateway-state-2`, restarted mocks.
Tested: `make rollback-test` (12 checks: dump and restore on a one-off PostgreSQL in an isolated network, the table after V7 returns with its rows, the V7 entry disappears, a failed restore changes nothing, a failed dump
aborts the backup, the rollback plan in `--dry-run` mode). Not tested on the stack: the steps with containers (`rm`, `stop`, `up`) and the order with waiting for the 4.x bundle.

### OpenBao: persistent storage (dev only)

Until 2026-11-02 OpenBao ran in `-dev` mode (memory, no volume): every container stop (also Stop in Docker Desktop) wiped
connection secrets, Authenticator TOTP seeds, Transit keys and AppRoles. This happened twice. Now:

- the server runs without `-dev`, configuration `openbao/server.hcl`: **single-node raft** storage on the named volume `openbao-data`. The `file` backend is out, because
  OpenBao 2.7.2 does not have it (`unknown storage type file`); raft needs no cluster ports or configuration beyond `node_id`;
- after start the server is sealed. The service `openbao-unseal` (`openbao/unseal.sh`, `restart: unless-stopped`) does an init on the first start
  (one key share, threshold 1) and stores the **unseal key and the generated root token** in `.secrets/openbao/` (directory 700, files 600, never to the log), and after
  every later server start it unseals the server from this file. This is dev only: one file on disk opens the whole storage. Production needs
  auto-unseal (KMS/HSM) or key splitting;
- the fixed stack token `BAO_ROOT_TOKEN` from `.secrets/dev.env` (used by `openbao-init`, smoke and scripts) is created by `openbao-unseal` as a token with the policy
  `root` and the same id; the service is healthy when OpenBao is unsealed and this token is valid, so `openbao-init` starts only then;
- `openbao` and `openbao-unseal` have `restart: unless-stopped`: they return after Stop/Start and after a Docker Desktop restart. The other services are unchanged (they return
  with `docker compose start`/Start in Docker Desktop);
- `openbao/init.sh` is safe on existing data: it creates Transit keys only when they do not exist, does not touch user secrets (`connections`, `authenticators`), writes the Service Desk
  service account only when it does not exist (a manual rotation survives a restart), and adds the GitLab and OpenSearch clients only when they
  differ from `.secrets/dev.env`;
- key protection: when the server is empty (another volume, for example after changing `COMPOSE_PROJECT_NAME`) and `.secrets/openbao/unseal-key` exists, `openbao-unseal`
  **refuses to init** and says so in the log (the service does not become healthy, `make up` stops). To init anyway: `BAO_ALLOW_REINIT=1` (`make reset` does this);
  the old files stay as `unseal-key.bak-<date>` and `root-token.bak-<date>` (600). `make clean` no longer removes `.secrets` when `down -v` failed;
- protection against an accidental switch: while OpenBao runs in `-dev` mode, every `up` (through `scripts/compose.sh`, and before `make up`, `up-core`, `up-full` and `up-m2`
  through the target `openbao-guard`) that would recreate the `openbao` container is rejected (code 3, `scripts/openbao-guard.sh`; it checks the plan with `--dry-run`). The switch is
  only through `make openbao-migrate`;
- broker: the AppRole login is lazy, and a 403 on an old token ends with a new login (`OpenBaoClient`), so after an OpenBao restart it recovers without
  a restart. While OpenBao is sealed (a moment after start) or not answering, operations end with 503 (fail closed), and after unsealing they work;
- **Boundary.** Safe: Stop/Start of containers or the project, a Docker Desktop restart, `docker restart`, `make down`, recreating the `openbao` container.
  Data-destroying: `make clean`, `make reset`, `docker compose down -v` and manually deleting the volume `openbao-data` (after also deleting `.secrets/openbao`, or without
  it: with an empty volume `openbao-unseal` does a new init and overwrites the keys). A volume without the file `.secrets/openbao/unseal-key` cannot be unsealed;
  the service says so in the log, and recovery means only deleting the volume. Removing a container without `-v` is safe;
- the one-off switch of a running stack: `make openbao-migrate CHECK=1` (plan and row counts in the broker database, no content), `make openbao-migrate CONFIRM=1`
  (execution; only the value 1). **Existing secrets are lost** (PAT/OAuth connections of all users, Authenticator registrations): what remains is what
  `openbao-init` recreates from `.secrets/dev.env`. The script touches only OpenBao (`--no-deps`) and restarts nothing else. A repeat (for example after a failure halfway) does not
  replace the already running OpenBao, but always runs `openbao-init` and the final checks;
- **moving the data is not possible** (checked on a one-off instance): Transit keys are created as non-exportable (`transit/export`: `private key
  material is not exportable`, `transit/backup`: an error), and the KV secrets are encrypted with those keys, so a KV copy without the keys is useless. The only way is the loss,
  which a human accepted;
- **After the switch** the rows in PostgreSQL stay (the script deletes nothing, also for alice, bob, carol, mallory). The portal therefore shows connections as `connected`
  and the Authenticator as `active`, although the secrets are gone, and registration gives 409 `already_registered`. For each user: first delete the connection in the portal
  (or `DELETE`) and connect again; for the Authenticator: first `make reset-authenticator USER=<login>` (the shared accounts alice, bob, carol, mallory need `FORCE=1` and
  belong to people), then register. `m5.py connections compare` counts database rows, so after the switch it sees no change; it now also reports `connected` rows
  of type `user-secret` without a secret in OpenBao (OAuth connections are not visible this way);
- **Return.** The data cannot be recovered: the old in-memory OpenBao disappears when the container is replaced. Reverting the switch means the previous compose definition (git) and recreating
  the `openbao` container, which gives an empty OpenBao `-dev` (losing everything after Stop again). The volume `openbao-data` and `.secrets/openbao` stay and do no harm. On return
  `openbao-init` creates the AppRole again, and users do the same as after the switch. A switch interrupted halfway (after the container is replaced, before `openbao-init`) ends with
  another `make openbao-migrate CONFIRM=1`;

Test: `make openbao-persist-test` (isolated network, the data volume and the key directory as a bind mount as in the stack, about 4 minutes, also the step `openbao` in `make ci`): a user secret, a Transit ciphertext and a manually
changed service account survive a restart of the server alone, stop and start of both containers, and deleting and recreating the container on the same volume; the old broker token is rejected by the new instance (403), and logging in again works;
an empty instance with an existing `unseal-key` does not get an init (the key file untouched), and with `BAO_ALLOW_REINIT=1` the old keys go to `.bak`; `init.sh` overwrites nothing and changes neither key versions nor the validity of
`secret_id`, a server without the sidecar stays sealed (broker login: 503), after a late sidecar start everything works, the unseal key and root token do not
appear in logs, key files have mode 600.

### Broker `secret_id` in OpenBao (the M4 stack too)

The broker AppRole has `secret_id_ttl=720h` (30 days, `BAO_SECRET_ID_TTL`; until 2026-11-02 it was 168h) counted from the creation of the `secret_id` (live most recently at `m4-switch`, 2026-10-29 with 168h, so it expires around 2026-11-03 to 2026-11-05; after `make openbao-migrate` it starts over).
A restart no longer recreates the `secret_id` (the storage is persistent), so `openbao-init` (`make up`, `make openbao-init`) renews it itself when less than 50% of the TTL is left; without running `init` within 15 days it will expire.
The storage is persistent now, so the `secret_id` survives an OpenBao restart with its remaining lifetime (test: the same expiry date before and after). The broker token lives up to 4 h (`token_max_ttl`), so after the `secret_id` expires an M4 broker running without a restart loses access to OpenBao after a few hours at the latest (reading and writing connection and
Authenticator secrets fails, people see `credential_required` or 5xx errors), and every broker restart (also in the switch) ends with a failed login. Prevention: `make openbao-renew`
(a one-off `openbao-init` container with `BAO_RENEW_SECRET_ID=1`: it destroys the valid `secret_id` and creates the same one again with the full TTL; it restarts nothing and changes only OpenBao). A plain `make openbao-init` (and `make up`) leaves a `secret_id` with more than half of its TTL alone, renews one with less left, and recreates an expired one; an expired entry stays in OpenBao until tidying, so `init.sh` runs `tidy` and retries creation (without that: `SecretID is already registered`; found by the persistence test). After expiry `make openbao-init` or `make openbao-renew` is enough; no broker restart is needed (the login is lazy), and the `secret_id` itself has the same value (`BAO_BROKER_SECRET_ID`). For the M4 stack the renewal must be done before that date regardless of M5; the switch does the same as its first step. Test: `make openbao-test` (isolated OpenBao, including the renewal) and `make openbao-persist-test` (an expired `secret_id` created again).

### Keycloak session times (2026-11-02)

`keycloak/realm-corp.json`: `ssoSessionIdleTimeout` 28800 (8 h, was 3600) and `ssoSessionMaxLifespan` 86400 (24 h, was 36000); `accessTokenLifespan` unchanged (900).
Reason: a break during the day should not force a new login. On the running Keycloak only these two fields were changed with a `PUT` on the realm through `kc_admin`
(`scripts/mcpdev.py`), without a restart; read before: 3600/36000, after: 28800/86400, access token 900.

Step-up and tests: the level `mfa` (LoA 2) has `loa-max-age` 0, and the BFF adds `max_age=0`, so a step-up asks for the password and OTP on every operation, regardless of the SSO session.
No test in the repository assumes the values 3600/36000. Level 1 (`corp-loa-1`) had `loa-max-age` 36000 (10 h), which could shorten the effective password session below 24 h; a human
accepted a 24 h maximum, so it was raised to 86400 in `realm-corp.json` and live (`PUT /authentication/config/<id>` through `kc_admin`, without a restart; before `{loa-condition-level: 1,
loa-max-age: 36000}`, after `{loa-condition-level: 1, loa-max-age: 86400}`; `corp-loa-2` unchanged: `loa-max-age` 0). After the change a one-off account: a password login gives `acr=password`,
with `acr_values=mfa`, OTP and `max_age=0` it gives `acr=mfa`, token 900 s. Behavior after 10 h and after 24 h was not measured (it needs waiting).

### What happens to sessions and data

| Data | Effect |
| --- | --- |
| MCP 4.x sessions in Redis (`gw:session:*`) | not recognized by gateway 5.x: the client gets `404` and runs `initialize` again; the keys disappear after the TTL, the script does not delete them |
| stored links (table `virtual_servers`) | migration V7 of the M5 gateway drops the table (confirmed by the gateway owners); before the change the script makes a full dump of the `gateway` database and a separate dump of the table (DDL and data) in `out/m5-backup-<time>/`, and rollback restores the table and removes the V7 entry from the Flyway history |
| `/v/<slug>/mcp` addresses in client configurations | stop working: the proxy does not route `/v/` to the gateway (it goes to the portal), and the M5 gateway would answer `404` anyway; people add `/mcp` with a filter (`claude mcp add ... "https://localhost:18745/mcp?systems=..."`); there is no transition period |
| activity rows with an old link name and the result `denied_link_scope` | stay in the database; the M5 gateway maps them on read |
| pending TOTP confirmations and rate counters in Redis | untouched; whether the keys were kept in a format the M5 gateway reads is confirmed by the gateway owners (in the worst case the user repeats the call) |
| connections (PAT, OAuth), Authenticators, OpenBao, the broker database | untouched; alice, bob, carol and mallory unchanged |
| `/app/state` (bundle rollback protection) | instance 1 keeps its volume; the state is copied to the volume of instance 2 before it starts, so the protection works from the first start |
| gateway internal JWT keys | from ephemeral to the file `.secrets/c2-jwks.json`; servers and the broker fetch the JWKS at the first token after a restart, as after every gateway restart in M4 |

Rollback is not automatic: the images from before the switch are in `out/m5-previous-images.txt`, and the gateway remembers the accepted bundle revision (rollback
protection), so returning to 4.x requires publishing the 4.x bundle again.

### After M5 acceptance

The M4 proxy files (`proxy/nginx.conf`, `proxy/routes.conf`, `proxy/to-gateway.conf`) stay unchanged until then, because they hold the `/v/` routes
of the running M4 stack (restarting the proxy before the switch would take the links away). After acceptance: `git mv proxy/m5/* proxy/` (overwriting three files),

## Mocks with controlled latency and 429 (for the load tests)

`mocks/systems/faults.py`, shared by the GitLab, Confluence, Service Desk and OpenSearch mocks. Settings on a running mock
(`PUT /__mock/faults`, Basic auth `admin:$MOCK_ADMIN_PASSWORD`, `GET` shows settings and counters, `DELETE` turns them off) or from start through the
variables `MOCK_LATENCY_MS`, `MOCK_LATENCY_JITTER_MS`, `MOCK_RATE_LIMIT_PER_SECOND`, `MOCK_RATE_LIMIT_BURST`, `MOCK_RATE_LIMIT_RETRY_AFTER`,
`MOCK_ERROR_STATUS`, `MOCK_ERROR_PERCENT`, `MOCK_FAULT_PATH_PREFIX`:

| Setting | Meaning |
| --- | --- |
| `latencyMs`, `jitterMs` | a fixed delay plus a uniform 0..jitter before handling (0..60000 ms) |
| `rateLimitPerSecond`, `burst` | a token bucket for the whole mock process; the excess gets `429 {"error":"rate_limited"}` with `Retry-After` |
| `retryAfterSeconds` | the value of `Retry-After` (default 1) |
| `errorStatus`, `errorPercent` | a 500..599 response for the given percentage of requests that passed the bucket |
| `pathPrefix` | only paths with this prefix (default `/`; for example `/api/`, so that `/oauth/token` is not slowed) |

Changes are in the mock's memory (they disappear after a restart) and do not apply to `/__mock/*`. More convenient: `make mock-fault ARGS="set gitlab latencyMs=200
rateLimitPerSecond=20 pathPrefix=/api/"`, `ARGS="show gitlab"`, `ARGS="clear all"`. The Jira mock is WireMock: `scripts/mock-fault.py set jira latencyMs=N`
sets a global delay (`POST /__admin/settings`, not checked on a running mock); a 429 for Jira is a stub through its admin API.
Running mocks have the old code until their first restart: `make m5-switch` restarts the three stateless ones; GitLab only on command (see above).
The mock journal (`/__mock/journal`) also records injected responses (status 429).

Fix L10: `describe_auth` in `mocks/systems/common.py` records a known PAT as `pat:<account>` (for example `pat:alice`), not the value; the fix of 2026-10-30
(`852a8f0`) is in the repository and covered by a test, and new code does not change it. The running GitLab mock has it only after a restart

## CI

The logic is in `ci/run.sh` (called by `make ci`); `.gitlab-ci.yml`, `Jenkinsfile` and `.github/workflows/ci.yml` are thin wrappers calling the same script, each with an explicit image `mcp-ci:local`
(variable `MCP_CI_IMAGE` in GitLab), without secrets. The job `static` (`lint mocks compose style`, no Docker daemon) runs for every change, also in a merge request; the job
`docker-tests` (`unit proxy lb`, with the Docker socket) only on the default branch. Steps: `lint` (`bash -n`, shellcheck at level warning, Python syntax), `mocks`, `unit` (mocks
plus `scripts/tests`, needs a CA generated in the container), `compose` (`scripts/check-compose.py`: rendering of the M3/M4/M5 layers, unique ports only on 127.0.0.1, TLS aliases only on
balancers, identical instance environment, shared keys, a registry without root and without deletion), `style` (`ci/check-style.py`), `proxy` (both layers), `lb`. Under `CI=true` a missing Docker
daemon or shellcheck is an error, not a skip; locally, steps with Docker are skipped with a message when there is no daemon. An unknown or empty step is code 2, and a failed step gives a nonzero result
(step functions return a status explicitly and do not rely on `set -e`). Tests use separate networks `mcp-dev-proxytest`, `mcp-dev-lbtest`, `mcp-dev-rollbacktest` and do not touch the stack containers.

- `ci/Dockerfile` (`mcp-ci:local`, built: bash, git, make, jq, curl, openssl, shellcheck, docker-cli with the compose plugin; no `ENTRYPOINT`, so that CI systems can run their own shell);
- `ci/runner.Dockerfile` (`mcp-ci-runner:local`): this image plus `gitlab-ci-local` 4.76.1, a local runner of `.gitlab-ci.yml` without a GitLab server, token or registration;
- `ci/local-runner.sh` / `make ci-local`: makes a one-off copy of the repository (a clone plus uncommitted files; without `.secrets`, `certs/` and `out/` of the real stack), mounts it under the same absolute
  path as on the host, and mounts the Docker socket. The `proxy` and `lb` steps in the container join the container to the test network and connect to the balancers by name (`curl --connect-to`), because `127.0.0.1` in a container is not the host.
  The socket gives the job full control over the host daemon, so run only this repository's code. Without `.dockerignore` the image build context would include the whole directory; `.dockerignore` excludes everything (the Dockerfiles copy nothing).
- **How to run the `ci/run.sh` of your own repo on this runner**: the repo needs `ci/run.sh` and a `.gitlab-ci.yml` with jobs calling the script with `image: $MCP_CI_IMAGE`
  (`mcp-ci:local`; for Java, an image with a JDK added to its own `ci/Dockerfile`). From the `mcp-platform-dev` directory: build the images once (`docker build -f ci/Dockerfile -t mcp-ci:local .` and `docker build -f ci/runner.Dockerfile -t mcp-ci-runner:local .`),
  then in the repo of the workstream `docker run --rm -v "$PWD:$PWD" -w "$PWD" -v /var/run/docker.sock:/var/run/docker.sock mcp-ci-runner:local <job>` (the same pattern as in `ci/local-runner.sh`; jobs with `image:` start
  as containers alongside and copy the working directory into volumes). Jobs that call Docker themselves with mounts from the working directory (like `proxy` and `lb` here) will not work inside a job container, because the daemon
  sees host paths: run such steps with `CI_MODE=image ci/local-runner.sh <steps>` (the same image, the same copy, the same path as on the host).
- The helper image of `gitlab-ci-local` (`firecow/gitlab-ci-local-util`, copying the working directory into volumes; approved by a human on 2026-10-31) is pinned to `sha256:1dc43cf4d8a4637a7da45eb95e14a97c750fbc9f1d45099bbd9f8ad6f0830778`: `ci/local-runner.sh` pulls it by digest and tags it `:latest`, which the tool uses.
- On GitHub and in Jenkins the `docker-tests` job in a container has the same path problem as above: it needs an agent on which the working directory has the same path in the container and on the host.
