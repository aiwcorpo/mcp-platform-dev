# M3 environment

Infrastructure for the Authenticator (TOTP confirmations), Cedar policies from a bundle, and activity logs. Scenario: `make m3`
(`scripts/m3.py`): infrastructure checks (PASS/FAIL) and steps that depend on the M3 components (SKIP until a component
has M3).

Portal UI labels are quoted in English below. The portal ships Polish labels by default (for example "Zarejestruj Authenticator"
for "Register Authenticator", "Katalog" for "Catalog").

## OpenBao

- Transit key `mcp-authenticators` (aes256-gcm96), separate from `mcp-credential-broker`: seeds can be rotated and
  revoked without touching credentials. The seed ciphertext sits under `secret/data/mcp/authenticators/<sha256(sub)>`
  (no envelope, per the mcp-contracts README 3.0.1, point 5 of the TOTP section).
- Additional broker AppRole policy: `secret/data/mcp/authenticators/*` (create, read, update, delete),
  `secret/metadata/mcp/authenticators/*` (read, list, delete), `transit/encrypt|decrypt/mcp-authenticators` (update).
  No `datakey`, rotation, configuration or key read.
- Applied to a running OpenBao by re-running `openbao-init` (idempotent; `make up` does the same).

## Redis: user `gateway`

The command list is in `redis/gateway.rules` (one source for `start.sh` and `redis-sync-acl.sh`), keys `gw:*`, channel
`credential.invalidated`. On top of the earlier set come: sets (`SADD`, `SREM`, `SCARD`, `SISMEMBER`, `SMEMBERS`),
sorted sets (`ZADD`, `ZREM`, `ZCARD`, `ZSCORE`, `ZCOUNT`, `ZRANGE`, `ZRANGEBYSCORE`, `ZREMRANGEBYSCORE`), `HSETNX`,
`HMGET`, `HLEN`, `SETEX`, `PSETEX`, `DECRBY`, `EXPIREAT`, `PEXPIREAT`, `PERSIST`, `WATCH`, `UNWATCH`, `EVAL`, `EVALSHA`.
`EVAL` is there so that the contract (atomic creation of a pending call and invalidation of the previous one, reserving
an attempt, compare-and-delete) can be met with a single script; Redis checks the script keys against `~gw:*`, and without
`SCRIPT` and `FUNCTION` nothing can be loaded or flushed. Still missing: `SCAN`, `KEYS`, `INFO`, `PUBLISH`, `CONFIG`,
`FLUSH*`. Give keys prefixes under `gw:` (for example `gw:confirm:pending:`, `gw:confirm:trace:`, `gw:confirm:count:`);
the gateway reports other commands to the environment owners.

## Keycloak: step-up MFA

- The flow `browser-corp` (the realm's browser flow): level 1 = password, level 2 = password + OTP
  (`Condition - Level of Authentication`, level 2 without SSO validity: OTP on every request of that level).
- The mapping `acr.loa.map`: `password` = 1, `mfa` = 2. A request with `acr_values=mfa` gives the claim `acr: "mfa"`, a regular
  login gives `acr: "password"`. The value for the BFF: `PORTAL_STEP_UP_ACR_VALUES=mfa` (set in compose for the BFF in the
  m2 image; the BFF sends `max_age=0`).
- OTP: TOTP SHA-1, 6 digits, 30 s, window +-1. The users `alice`, `bob`, `carol` have OTP configured; `mallory`
  does not. A step-up for a user without OTP is rejected (HTTP 400, no token): the required action `CONFIGURE_TOTP` is disabled in the realm,
  so a password alone does not give the `mfa` level through self-service OTP setup (negative test in `make m3`). In production the second factor must
  be registered outside the step-up session. Guess protection (`bruteForceProtected`): a threshold of 30 failures in a 12 h window, a lockout growing by
  60 s up to 15 min, no permanent lockout; the threshold is high so that negative tests do not lock accounts.
- Seeds are generated by `scripts/init-secrets.sh` into `.secrets/dev.env` (`KC_USER_<NAME>_OTP_SEED`, Base32); the realm gets
  them as environment variables, and nothing in the repo contains them. `make users` prints passwords, never seeds; the code comes from `make otp`, and the seed
  (as an `otpauth://` URI) only from a deliberate `make otp URI=1`. Do not paste seeds or `otpauth://` URIs into an agent chat, notes or shell history.
  Rotating the seeds and the Keycloak admin password (the script prints nothing):

  ```bash
  python3 - <<'PY'
  p = ".secrets/dev.env"
  lines = open(p).read().splitlines()
  keep = [l for l in lines if not (l.startswith("KC_USER_") and "_OTP_SEED=" in l) and not l.startswith("KC_BOOTSTRAP_ADMIN_PASSWORD=")]
  open(p, "w").write("\n".join(keep) + "\n")
  PY
  make secrets
  scripts/compose.sh --profile full --profile m2 up -d --no-deps --wait keycloak
  ```

  Recreating Keycloak breaks SSO and portal sessions; user `sub` values stay (fixed `id` in the realm). The new admin password: `make admin-password`
  (it is not in `make users`: the master admin can change the step-up flow). Whoever added the `otpauth://` URI to an app must add it again.
- User `sub` values do not change (fixed `id` in `realm-corp.json`).
- A realm change requires recreating the Keycloak container (import at startup): `compose up -d --no-deps keycloak`
  (done; SSO and portal sessions were broken).

### How to pass MFA in dev (human)

1. Log in to the portal (`https://localhost:18745`) with the password from `make users`.
2. An operation with step-up (registering the Authenticator) redirects to Keycloak and asks for the OTP code.
3. The code: `make otp USER=alice` (the current code and its validity time). The code is valid for 30 s; after use the next one comes only in the
   next clock step.
4. To use your own app instead of `make otp`: `make otp USER=alice URI=1` prints the `otpauth://` URI (it contains the seed,
   dev only) to scan or paste.
5. This is the Keycloak login OTP (it replaces Entra MFA). The platform Authenticator (the confirmation code for
   `delete_issue`) is a separate TOTP account with a seed issued by the broker when registering in the portal.

## Policy bundle server

The `policies` service (nginx, GET/HEAD only): `http://localhost:18747/policies/{main,overrides}/latest.json` and the files
`policies-<revision>.tar.gz[.sig]`; in the `core` and `servers` networks as `http://policies.internal:8080`. `latest.json`
has `Cache-Control: no-cache` and `ETag`; archives are immutable (`immutable`); files starting with a dot
(`.publish.lock`) are not served. The source directory: `POLICY_REPOSITORY_DIR` in `.env` (default
`../mcp-policies/out/repository`, read only), so the `.ci/pipeline.sh` of the policies repo publishes without changes. The server is not
a trust point: the recipient verifies the signature itself with the public key from `mcp-policies/keys/dev/`. Port 18747
instead of the proposed 18095 (the environment's port range). Publishing with `PUT` is not supported (nginx does not check `If-Match`).

## CN `mcp-offboarding` and Authenticator reset

The certificate `certs/mcp-offboarding` (clientAuth) was already in `gen-certs.sh`. `make reset-authenticator USER=alice`
calls `POST /v1/admin/users/{sub}/authenticator/reset` over mTLS with that certificate (no bearer; `sub` from a real
login; `BROKER_URL` as in `make pat`, default broker `:18100`). The verification lockout (5/15 min) is not
lifted; that is a property of the contract.

## Jira mock

`DELETE /rest/api/2/issue/{key|id}` -> 204 for a known PAT, 404 for an unknown issue, 401 without a known PAT; stateless
(the issue stays readable), the evidence is the journal: `make jira-auth`. Requires the `mcp-jira` server with the
`delete_issue` tool.

## `make m3`

61 checks, 0 SKIP on a stack with the M3 components: infrastructure (OpenBao, Redis, Keycloak, bundle server, certificate, Jira mock), the registry
(`tools/list` through the gateway for five servers) and the Authenticator scenario (registration with step-up and a TOTP from the seed in the response,
`delete_issue` -> `confirmation_required`, preview, `viewed`, wrong code, execution with the code, rejection of a repeated code, cancellation, lock after preview,
Cedar denial for `bob`, `/activity/calls`). When a component has no M3, the step is a SKIP with a reason. It changes state: see "`make m3` changes state" below.

## M3 component integration (milestone M3.3)

Images in `.env`: gateway `mcp-gateway:m3-7315893`, broker `mcp-credential-broker:m3-b4dd446`, BFF `mcp-portal-bff:m3-44dc221`,
web `mcp-portal-web:m3-de48d2f`. MCP servers on starter beta-3: jira `m3-198c8ca`, confluence `m3-759efc6`, gitlab `m3-c234e67`, servicedesk `m3-549cf02`, opensearch `m3-dae2b19`.

- Gateway: volume `gateway-state` on `/app/state` (protection against bundle rollback), `MCP_POLICY_*` (bundles from
  `http://policies.internal:8080/policies/{main,overrides}/`, dev public keys `test-policies-*` mounted from
  `../mcp-policies/keys/dev`, `MCP_POLICY_ALLOW_TEST_KEYS=true` only in dev), `MCP_ACTIVITY_CURSOR_KEY` (generated into
  `.secrets`). The image is glibc-based without `wget`, so the healthcheck opens a socket through `bash`. Startup loads the bundle:
  `policy bundle main loaded: revision ...` in the log.
- Registry (mode `required`): in dev the manifests are taken by `MCP_REGISTRY_BOOTSTRAP=true` (the gateway fetches the server's `/mcp-manifest` without
  a registry row). The CI script (`PUT /admin/v1/registry/servers/{id}` with CN `mcp-registry-ci`) is not simple in dev:
  the manifest is served only to a server called with the gateway certificate and the gateway service JWT, so bootstrap stays.
  To change a tool definition (a new `definitionHash`): `make registry-refresh` (dev only: removes the rows taken over by bootstrap
  and recreates the gateway, which fetches the manifests again; it does not touch `ci` rows). Bootstrap has no profile guard in the gateway:
  do not move `MCP_REGISTRY_BOOTSTRAP` outside this stack (reported to the gateway owners).
- MCP servers: `MCP_POLICY_*` (bundle `https://policies.internal:8443/policies/main/latest.json`, trust through the bundle
  `mcp-internal-ca`), state volumes `mcp-<system>-state` (created by the one-shot service `server-state-init`), `MCP_INTERNAL_URL`,
  `MCP_ACCEPTED_CREDENTIAL_TYPES`. Servers (starter 3.0.0-beta-4) run with the profile `devstack`
  (`SPRING_PROFILES_ACTIVE=devstack` and the acknowledgements `MCP_DEVSTACK_ACKNOWLEDGED`, `AIWCORPO_MCP_PLATFORM_DEVSTACK_ACKNOWLEDGED`,
  `AIWCORPO_MCP_PLATFORM_POLICY_ALLOW_TEST_KEYS`): this lifts only the ban on `test-*` policy bundle keys
  (`MCP_DEVSTACK_ACKNOWLEDGED` must be a real process variable: an `environment:` block in compose satisfies it; the compose `.env` file
  alone is not enough). The gateway JWT is signed with ephemeral keys, so the flag for the JWT is not set); the rest (mTLS, https for bundles, `state-dir`) applies as in production. The bundle key has its id `test-policies-main-dev` again; every start
  logs `WARN event=devstack_profile`. (In beta-3 the dev key was briefly configured under the id `policies-main-dev`, which bypassed the check
  by name; that workaround was removed.) `make m3` checks that every bundle key in compose comes from `mcp-policies/keys/dev`. The bundle server has a second
  https listener on :8443 (certificate `certs/policies`, internal CA); the gateway still downloads over http :8080 (traffic inside the `core` network).
- The Confluence mock has `GET /rest/api/space/{key}?expand=metadata.labels` (HR `restricted`), because the server reads space classification.
- `MCP_GITLAB_FILE_MAX_BYTES` must not exceed 262144 (the beta-3 starter refuses to start).
- Redis: `appendonly yes`, `maxmemory-policy noeviction`, persistent volume `redis-data` on `/data` (confirmation state, counters and locks
  survive recreating the container). `redis/start.sh` reads the rule files before writing the ACL and fails when they are missing.
- The Transit key `mcp-authenticators` has `derived=false`: the ciphertext is not bound to a context, but the decrypted record contains `sub`,
  which the broker compares with the request (a contract requirement), and the ciphertext sits under a path built from `sha256(sub)`. This is a deliberate decision,
  unchanged; `derived=true` with the context `sha256(sub)` is a possible contract-change proposal for the broker.
- Private keys: the host's `certs/*/tls.key` have mode 600; containers mount only the `keystore.p12` of their own identity. On Linux all
  mode-600 files mounted into containers (`keystore.p12` and `truststore.p12` for uid 999 of the servers and gateway, the Keycloak `tls.key` for uid 1000, the proxy key for uid 101) would be unreadable,
  because the owner is the host uid (Docker Desktop on macOS ignores this); not verified. The Linux fix: a one-shot init service copying the files with the container owner, like `server-state-init`.
- BFF: no `idp-relay` and no `JAVA_TOOL_OPTIONS`, `PORTAL_OIDC_*` with separate addresses, `PORTAL_STEP_UP_ACR_VALUES=mfa`.
- Known shared-database problem: a gateway started on the host by another workstream writes the `mcp-jira` manifest to the stack's
  PostgreSQL (`registry_servers`, `internalUrl` with a host port); the gateway container then rejects it. Deleting the
  row with `source='bootstrap'` fixes it, and the host gateway should use its own database.

### Step by step for a human (M3 in the browser and in Claude Code)

From scratch: `make up-full` (after `make images`), `make images-m2` and `make up-m2`; you also need a published policy bundle in
`POLICY_REPOSITORY_DIR` (default `../mcp-policies/out/repository`, `latest.json` in `main/` and `overrides/`) and the public keys
`../mcp-policies/keys/dev/test-policies-*-dev.public.pem` (without them mounting the files fails). Then you need a running stack
(`make ps`: everything `healthy`) and alice's password from `make users` (it prints passwords, not seeds).

**Warning:** the seed of the "MCP Platform" account and TOTP codes must not be pasted into an agent chat, notes or the shell. The seed goes only into the Authenticator
app. A code typed to an agent stays in the conversation transcript; it is single-use and useless after use, but do not type a code you have not used yet.

**Two different codes, do not mix them up**

| Code | Used for | Source |
| --- | --- | --- |
| Keycloak login OTP | the additional factor at a step-up login (replaces Entra MFA) | `make otp USER=alice` (seed from `.secrets/dev.env`) |
| "MCP Platform" code from the Authenticator | confirming a destructive action (`delete_issue`) in a conversation with the agent | the Authenticator app on the phone, from the seed issued once when registering in the portal |

Both are 6 digits every 30 s, but they are two separate TOTP accounts with different seeds. A code is single-use: the same code does not work twice in
one clock step; wait for the next code.

**1. Trust the CA and log in to the portal**

1. `make trust-ca` prints the commands (it runs nothing); run point 1 (the macOS keychain) and point 2 in the shell from which you will start `claude`:
   `export NODE_EXTRA_CA_CERTS=<repo directory>/certs/public-ca/ca.crt` (absolute path).
2. Open `https://localhost:18745` and log in as `alice` (password from `make users`).

**2. Register the Authenticator (once)**

1. In the portal go to Catalog; the banner "Register Authenticator" leads to the page "Authenticator registration" (`/authenticator`).
2. The registration button requires a fresh MFA: Keycloak asks again for the password and for the **login OTP**. Enter the code from `make otp USER=alice`
   (did it expire while you filled in the form? Run the command again and enter the next one).
3. The portal shows a QR code and the seed of the "MCP Platform" account **only once**. Scan the QR with the Authenticator app (or enter the seed by hand).
   The seed cannot be read later.
4. Enter the first code from the app (the "MCP Platform" account, not `make otp`) and confirm. The status changes to "active".

**3. Prepare an address with the `jira__delete_issue` tool**

The description for the M3 and M4 stacks was about a stored link from the wizard ("My links", `/v/<identifier>/mcp`). Since M5 there are no links: the `/mcp` address covers the whole
platform, and the filter is in the query and grants nothing (permissions are computed by Cedar on every call).

1. The address wizard in the portal (`GET /api/v1/me/mcp-endpoint`) builds the address and stores nothing.
2. Choose Jira tools: `jira__delete_issue` (the tool "Deletion", marked as requiring a code from the Authenticator; alice has the group
   `mcp-jira-destructive`, bob does not), plus for example `jira__get_issue`: `https://localhost:18745/mcp?tools=jira__delete_issue,jira__get_issue`.
3. The screen shows the `claude mcp add ...` command and a "Copy" button. Without the wizard you can also use the whole server: `https://localhost:18745/s/mcp-jira/mcp`.

**4. Add the server in Claude Code**

In a shell with `NODE_EXTRA_CA_CERTS` set (see point 1):

```bash
claude mcp add --transport http --client-id claude-code --callback-port 33418 deletion "https://localhost:18745/mcp?tools=jira__delete_issue,jira__get_issue"
claude
```

In `claude` type `/mcp`, choose the server `deletion` -> Authenticate. A browser opens with the Keycloak login (alice, password; the login OTP is not required
here). After returning, the server has the status "connected". Jira must be connected in the portal ("Connect", PAT `alice-pat`); otherwise the agent gets
`credential_required` with a link to the portal.

**5. Delete an issue with a code**

1. Tell the agent: `Delete issue ABC-2 in Jira.` (ABC-2 exists in the mock and is not restricted for alice; HR-1 is in the Restricted project).
2. The agent gets `confirmation_required` with a description of the operation and a preview address (`previewUrl`, valid 120 s) and asks for a code.
3. Optionally open the preview from that address in a browser logged in to the portal: you will see the operation computed by the gateway (not the agent's description).
   From the moment the preview is opened, another destructive operation is blocked (`confirmation_blocked`) until this one expires (2 min) or is cancelled
   with the "Cancel" button in the preview.
4. Read the current 6-digit code of the "MCP Platform" account from the Authenticator app and tell the agent: `Code: 123456, retry the deletion.` The agent repeats the same
   call with the extra field `confirmation_code`. You have 3 attempts; 5 wrong codes in 15 min lock verification for 15 min.
5. On success the agent answers `{"issueKey":"ABC-2","deleted":true}`. In the portal, "Audit logs" (`/logs`), there is one row for this call
   (result confirmed; cancelled and expired ones are visible too); the log contains no code or seed.
6. The Jira mock keeps no state: issue ABC-2 can still be fetched, and the evidence of deletion is the mock journal (`make jira-auth`, the row
   `204 DELETE /rest/api/2/issue/ABC-2 PAT alice-pat`). There is nothing to restore; the Jira mock has no state to reset, and `docker restart mcp-dev-jira-mock-1` clears only the request journal.
7. Cancelling: ask to delete another issue (for example ABC-1), open the preview and click "Cancel"; repeating with a code ends with `confirmation_cancelled`.
   After cancelling, wait 30-60 s for the next code (the codes are burned).

### `make m3` changes state

`make m3` does not restart the stack, but it **deletes alice's Authenticator** (reset through `mcp-offboarding`), registers a new one with its own seed (you lose the registration from the
phone and must register the Authenticator again as in point 2), connects alice's Jira with the PAT `alice-pat`, and sends `DELETE ABC-2` to the Jira mock. It leaves
entries in the audit logs. It takes several minutes, because it waits for successive TOTP clock steps. Result: 61 PASS / 0 FAIL / 0 SKIP
(infrastructure, registry, Authenticator scenario). Do not run it during a manual demo on the same account.

### Switching the gateway to the devstack profile (prepared)

The gateway `mcp-gateway:m3-1f7f543` refuses to start without the `devstack` profile. Compose has `SPRING_PROFILES_ACTIVE=devstack`, `MCP_DEVSTACK_ACKNOWLEDGED=true`,
`AIWCORPO_MCP_PLATFORM_DEVSTACK_ACKNOWLEDGED=true` and only the relaxations the stack uses: `MCP_POLICY_ALLOW_TEST_KEYS`, `MCP_ALLOW_PLAIN_HTTP`,
`MCP_REGISTRY_BOOTSTRAP` (the registry stays in mode `required`, not `static`); the http addresses of the IdP, the bundle server and `MCP_POLICY_STATE_DIR` are unchanged.
The gateway JWT is signed with ephemeral keys, so `MCP_INTERNAL_JWT_ALLOW_TEST_KEYS` is not set.

To apply it on a running stack (without down/clean/reset, state stays): `make m3-switch` (`scripts/apply-m3-switch.sh`) recreates in turn the broker,
the five MCP servers and the gateway, and checks `event=devstack_profile` in the gateway and server logs. Then: `make proxy-test`, `make m1`, `make m2`,
`make m3` (deletes alice's Authenticator; it contains the gateway `event=devstack_profile` test, which is a SKIP until applied), `mcp-e2e/run-m2.sh`.

### Replacing the "dev public" CA (2026-10-29)

The native Claude Code rejected a CA with a name constraint of the IP type (`UNSUPPORTED_CONSTRAINT_TYPE`). The new CA has only `permitted;DNS:localhost`
(server certificates still have `127.0.0.1` and `::1` in the SAN). After regeneration (`scripts/gen-public-cert.sh`) the old CA must be removed from the keychain
and the new one added; both have the same name, so remove by SHA-1 (`make trust-ca` prints the commands). Claude Code takes `NODE_EXTRA_CA_CERTS`
from the `env` block in `~/.claude/settings.json` before the shell variable, so the macOS keychain is more reliable (command 1 of `make trust-ca`).
